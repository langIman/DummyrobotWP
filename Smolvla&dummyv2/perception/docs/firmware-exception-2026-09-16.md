# 22:29 主控异常终止现场

## 已确认事实

运行桥接已采用 `nonblocking_poll_v1`。22:29:21.499，事务 26323 发送
`>-0.120,-19.668,124.814,1.175,31.156,1.177,8.000`（包括换行 49 字节）。
事务 26324 在 500.93 ms 后返回：

```
terminate called after throwing an instance of '
```

该文本直接来自 COM7 原始回复；在实机 Flash 备份 `flash-read1.bin` 中亦找到
相同提示，地址 `0x08039908`。异常类型名没有收到，不能由此断定是 `bad_alloc`。
固件备份还包含 `bad_alloc` 字符串，但存在该字符串不能证明此次抛出的是它。

之前一次完整反馈为 `[-0.12, -19.58, 124.65, 1.20, 31.43, 1.19]`，
与最后目标最大相差约 0.274°；之前运动确认耗时约 2–4 ms。
因此此次退出并非 8°差值阈值或奇异性保护，也不是把正常 `ok` 误判为失败。

紧接着夹爪失能等待 4.52 秒超时；随后六轴 STOP/DISABLE 因 COM7 拒绝访问
未发送。网页“已停止”只能表示停止产生新目标，不能代表实机已停或失能。
现场日志已保存在 `runtime/motion-fault-20260916-222921/transport.jsonl`。

## 排查边界

参考源码的命令入队和出队使用 `std::string`，分属通信任务与命令处理任务；
动态分配、队列字符串及堆线程安全值得继续检查，但这只是候选路径。
参考源码已包含早期本地修改，且与实机版本不同，不能把参考行号当作实机故障点。
没有连接 ST-LINK 时无法进一步保留 MCU 内存现场；异常类型和具体抛出点尚未确认。
不更换固件，不提高超时掩盖异常，不自动重发运动命令。

## 已补充的软件处理

- 将该回复识别为 `controller_firmware_exception`，使能锁存改为 unknown 并记录原文。
- 六轴 STOP、DISABLE 先于夹爪失能，避免夹爪事务阻塞六轴停止尝试。
- 故障处理状态暴露急停确认结果；网页区分停止发目标与硬件失能，确认失败时明确提示。

这些改动完善故障处理，不是对 MCU 异常终止的根治。仍需故障现场或与实机匹配的
源码/符号定位异常，不能仅靠只读串口压力测试宣称已解决运动中的固件故障。
